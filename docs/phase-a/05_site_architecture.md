# ช่วง ก. ข้อ 5 · โครงเว็บ ผังการใช้งาน และรูปแบบข้อมูลคลังข้อสอบ (ร่าง 15 พ.ย. 2569 รอบอสอนุมัติ)

ยังไม่มีโค้ด เอกสารนี้คือแบบที่ช่วง ข. จะสร้างตาม · จุดที่ตัดสินใจแล้วมีเหตุผลกำกับ เพื่อให้ตัวที่มาทำต่อไม่ต้องเดา

## 1. การตัดสินใจเชิงสถาปัตยกรรมที่แก้ทีหลังยาก

### 1.1 เนื้อหาที่ขายต้อง**ไม่อยู่ในไฟล์สแตติก** (สำคัญที่สุด)
เว็บสแตติกบน Cloudflare Pages ทุกไฟล์ใน `dist/` ใครก็ดาวน์โหลดได้ ถ้าใส่คลังข้อสอบและเฉลยไว้ใน JS/JSON ของเว็บ คนจะดึงไปทั้งคลังโดยไม่จ่าย ต่างจากเกมครัวที่เนื้อหาฟรีอยู่แล้ว
- `dist/` มีเฉพาะ: หน้าเว็บ · **โจทย์**ของแบบวัดความพร้อมฟรี (ไม่มีเฉลย ไม่มีเหตุผล) · ผังหลักสูตร (ชื่อหน่วย/หัวข้อ จำนวนข้อ)
- คลังเสียเงิน (โจทย์ ตัวเลือก เฉลย เหตุผล แหล่งอ้างอิง) อยู่ในตาราง Supabase `exam_items` ที่ RLS **ปิดการอ่านตรงทั้งหมด** · เข้าถึงผ่าน Edge Function `exam-api` เท่านั้น ซึ่งตรวจสิทธิ์จาก `exam_entitlements` ก่อนส่งข้อ
- การตรวจคะแนนแบบวัดฟรีทำที่ `exam-api` (ส่งคำตอบไป ได้คะแนนรวม+รายหน่วยกลับมา) เฉลยจึงไม่หลุดไปที่เบราว์เซอร์ · ผู้ไม่ล็อกอินเรียกได้ (จำกัดอัตราต่อ IP)
- ผลที่ตามมา: แบบฝึกและชุดจำลองต้องออนไลน์ · ยอมรับได้ (ผู้ใช้จ่ายเงินและล็อกอินอยู่แล้ว)
- ทางเลือกที่ไม่เลือก: เข้ารหัสคลังไว้ในไฟล์สแตติกแล้วแจกกุญแจหลังจ่าย (กุญแจเดียวหลุดคือหลุดทั้งคลัง)

### 1.2 เซิร์ฟเวอร์เป็นผู้ประกอบชุดข้อสอบ
`exam-api` สุ่มข้อตาม blueprint ของสนาม โดย**เลี่ยงข้อที่ผู้ใช้เคยเจอ** (จาก `exam_seen`) แล้วบันทึกชุดเป็น `exam_attempts` · ทำให้ "ทำซ้ำได้โดยข้อไม่ซ้ำเดิม" และกันการขูดทั้งคลังในครั้งเดียว (จำกัดจำนวนชุดต่อวัน)

### 1.3 ใช้โปรเจกต์ Supabase ของเกมครัวร่วมกัน (ตามคำสั่งบอส)
- โปรเจกต์ `tayak-kitchen` (ref อยู่ใน `tayak-cefr/CLAUDE.md`) · ผู้ใช้ `auth.users` ใช้ร่วมกัน (คนเดียวล็อกอินได้ทั้งสองผลิตภัณฑ์)
- **ทุกอย่างของเราขึ้นต้นด้วย `exam_`** (ตาราง ฟังก์ชัน SQL นโยบาย) และ Edge Function ขึ้นต้นด้วย `exam-` · ห้ามแก้/ลบ `orders` `entitlements` `saves` `comp_list` `event_passes` `item_reports` และฟังก์ชัน `billing` `beam-webhook` ของเกมครัว
- ตาราง `orders` ของเกมครัวมี check `plan in ('month','year')` จึง**ไม่ใช้ร่วม** สร้าง `exam_orders` แยก
- ⚠️ ข้อมูลผู้ใช้ของสองผลิตภัณฑ์อยู่ฐานเดียวกัน → นโยบายความเป็นส่วนตัวของเว็บนี้ต้องบอกชัด และหน้า PDPA ของเกมครัวอาจต้องเพิ่มประโยค (บอสตัดสิน)
- ทุกไฟล์ SQL เก็บใน `supabase/sql/` เป็น "เพิ่มอย่างเดียว" และ**ไม่รันเองจนกว่าบอสอนุมัติทีละไฟล์**
- การตั้งค่า Auth (Google) ใช้ของเดิม ต้องเพิ่ม URL ของเว็บใหม่ใน Redirect URLs (บอสทำในแดชบอร์ด)

### 1.4 Beam: webhook ปลายทางเดียวกันหรือแยก (ยังไม่ตัดสิน)
เกมครัวมี `beam-webhook` รับเหตุการณ์จ่ายเงิน ถ้าบัญชี Beam เดียวกันตั้ง webhook ได้ปลายทางเดียว ต้องเลือก:
- ก. (แนะนำ) `exam-billing` สร้าง Payment Link แล้วใช้การ **verify ตอนผู้ใช้กลับจากหน้าจ่าย + ถาม Beam ซ้ำเป็นระยะ** (แบบ `cloud.verifyLadle()` ของเกมครัว) ไม่พึ่ง webhook · ไม่แตะฟังก์ชันของเกมครัวเลย
- ข. แก้ `beam-webhook` ของเกมครัวให้ส่งต่อเหตุการณ์ของ exam (แตะของเดิม ต้องขออนุมัติ)
- ต้องอ่าน docs.beamcheckout.com ว่าตั้ง webhook หลายปลายทางได้หรือไม่ก่อนสรุป (ตัวที่มาทำต่อ)

### 1.5 เทคโนโลยีฝั่งหน้าเว็บ
- HTML/CSS/JS ล้วน ไม่มี framework · build ด้วย Python (แบบ `kitchen_src/build.py`) → `dist/` · เหตุผล: ทีมคุ้น เบา โหลดเร็วบนมือถือ ไม่มี dependency ที่ต้องดูแล
- หลายหน้า (ไม่ใช่ไฟล์เดียวแบบเกม) เพื่อ SEO และ Open Graph ต่อหน้า · ใช้แม่แบบร่วม (`src/layout.html`) + JS ร่วม `app.js`
- ออกแบบมือถือกว้าง 390 เป็นหลัก · โทนจริงจัง: พื้นขาว ตัวอักษรเข้ม สีหลักเดียว ไม่มีตัวการ์ตูน · **ห้ามใช้ `text-shadow` กับข้อความไทย** (บทเรียนจากเกมครัว 6 พ.ย.)
- ความคืบหน้าระหว่างทำข้อสอบเก็บ localStorage (ห่อ try/catch) เพื่อไม่ให้หายเมื่อเน็ตหลุด แล้วส่งขึ้นเมื่อส่งชุด

## 4. ฐานข้อมูล (ร่าง ยังไม่รัน · ทุกตารางเปิด RLS)
| ตาราง | คอลัมน์หลัก | ใครอ่าน/เขียน |
|---|---|---|
| `exam_items` | `id` text PK · `exam` · `unit` · `topic` · `kind` · `level` · `body` jsonb (โจทย์ ตัวเลือก เฉลย เหตุผล แหล่ง) · `status` (draft/approved/retired) · `version` · `updated_at` | service role เท่านั้น (ไม่มี policy) |
| `exam_orders` | `id` uuid · `user_id` · `product` · `round` · `amount` · `list_amount` · `provider_link_id` · `provider_url` · `status` · `created_at` · `paid_at` · `credited_at` | เจ้าของอ่านได้ · เขียนผ่าน service role |
| `exam_entitlements` | `user_id` · `product` · `round` · `expires_at` · `source` (order/comp) · PK (`user_id`,`product`,`round`) | เจ้าของอ่านได้ · เขียนผ่าน service role |
| `exam_attempts` | `id` uuid · `user_id` (null ได้สำหรับแบบวัดฟรี) · `exam` · `mode` (check/unit/practice/mock) · `item_ids` · `answers` jsonb · `score` jsonb (รวม+รายหน่วย) · `started_at` · `submitted_at` | เจ้าของอ่านได้ · เขียนผ่าน exam-api |
| `exam_seen` | `user_id` · `item_id` · `n_seen` · `n_wrong` · `last_at` · `last_correct` | เจ้าของอ่านได้ · เขียนผ่าน exam-api |
| `exam_reports` | `id` · `item_id` · `user_id` (null ได้) · `why` · `note` · `created_at` | insert ได้ทุกคน · อ่านเฉพาะ service role (แบบ `item_reports` ของเกมครัว) |
| `exam_rounds` | `exam` · `round` · `exam_date` (null ได้) · `expires_at` · `on_sale` | อ่านได้ทุกคน · เขียนผ่าน service role |

- ข้อมูลส่วนบุคคลที่เก็บ: อีเมล (จาก Google ผ่าน auth) + ผลการทำข้อสอบ + คำสั่งซื้อ · ไม่เก็บชื่อจริง เบอร์โทร โรงเรียน · ผู้ใช้ลบข้อมูลของตัวเองได้จากหน้าบัญชี
- Edge Functions: `exam-api` (check-grade · next-set · submit · explain · report-data) · `exam-billing` (status · checkout · verify) · ราคาอยู่ใน `exam-billing/pricing.ts` เป็นฟังก์ชันล้วนที่เทสต์ได้
- ความลับ (`BEAM_*`, service role) ตั้งใน Supabase โดยบอส Claude ไม่เห็นค่า

## 5. รูปแบบข้อมูลคลังข้อสอบ

### 5.1 ไฟล์ต้นทาง (สิ่งที่คนเขียนข้อแก้)
- ที่อยู่: `bank/<exam>/<unit>.yaml` (ไฟล์ละหน่วย) · YAML เพราะข้อความไทยหลายบรรทัด อ่านและ diff ง่าย ตรวจโครงสร้างด้วย schema ได้ · (เกมครัวใช้ .txt แบบกำหนดเอง ซึ่งเพิ่มฟิลด์ยาก จึงไม่ยืม)
- รหัสข้อ: `<exam>-<unit>-<เลข 4 หลัก>` เช่น `kpc-a5-0012` · **ไม่เปลี่ยนตลอดชีวิตของข้อ** (ประวัติผู้ใช้ผูกกับรหัส) แก้เนื้อหาให้เพิ่ม `version`

```yaml
- id: kpc-b3-0007
  unit: b3.1            # ต้องมีใน bank/<exam>/_blueprint.yaml
  topic: child-protection
  kind: mcq             # mcq | set (ข้อความ/บทอ่านร่วม หลายข้อย่อย) | order | essay (สถานการณ์ + แนวคำตอบ)
  level: 2              # 1 จำ/เข้าใจ · 2 ประยุกต์ · 3 วิเคราะห์สถานการณ์
  stem: |
    (โจทย์ เขียนใหม่ทั้งหมด)
  choices:              # 4 ตัวเลือกเสมอสำหรับ mcq · ตัวแรก = ข้อถูก (build สลับลำดับให้)
    - text: ...
      why: เหตุผลที่ถูก อ้างข้อกฎหมาย/หลักการ
    - text: ...
      why: เหตุผลที่ผิด (ผิดเพราะอะไร สับสนกับอะไร)
    - text: ...
      why: ...
    - text: ...
      why: ...
  explain: |            # สรุปหลักที่ควรจำ 1–3 บรรทัด
  sources:              # บังคับเมื่อหน่วยถูกทำเครื่องหมาย legal: true ใน blueprint
    - title: พระราชบัญญัติ... พ.ศ. ....
      ref: มาตรา ..
      as_amended: ฉบับที่ .. พ.ศ. ....
      url: https://...   # แหล่งทางการ
      verified_at: 2026-11-15
  valid_for: null       # เช่น "FY2570" สำหรับนโยบายรายปี
  status: draft         # draft → approved (บอสตรวจ) → retired
  version: 1
  author: claude
  note: (บันทึกถึงผู้ตรวจ ไม่แสดงผู้ใช้)
```

### 5.2 Blueprint ของสนาม (`bank/<exam>/_blueprint.yaml`)
กำหนด: รายการหน่วย/หัวข้อ (ชื่อไทยตามหลักสูตร) · `legal: true/false` · สัดส่วนข้อในชุดจำลองแต่ละแบบ (`mock_full`, `check_free`) · คะแนนต่อข้อ · เวลา · เกณฑ์ผ่าน · แหล่งอ้างอิงของโครงสร้าง (เลขหนังสือ วันที่) · `confirmed: true/false` ต่อค่า เพื่อให้หน้าเว็บแสดง "ตามหลักสูตรทางการ" เฉพาะค่าที่ยืนยันแล้ว

### 5.3 ตัว build และตัวตรวจคุณภาพ (สร้างในช่วง ข. ข้อ 6)
`python3 bank/build.py` → `build/items.json` (สำหรับอัปโหลดเข้า `exam_items`) + `dist/data/<exam>_check.json` (โจทย์แบบวัดฟรี ไม่มีเฉลย) + `dist/data/<exam>_blueprint.json`
`python3 bank/check_bank.py` ต้องผ่านก่อน commit · กติกาที่ตรวจอัตโนมัติ:
1. โครงสร้างครบตาม schema · รหัสไม่ซ้ำ · หน่วย/หัวข้อมีใน blueprint
2. mcq มี 4 ตัวเลือก ไม่ซ้ำกัน · ทุกตัวเลือกมี `why` ยาวพอ (≥ 15 ตัวอักษร) และ `why` ของตัวผิดไม่ซ้ำกันเอง
3. **ความยาวคำตอบถูก:** ต่อหน่วย ข้อถูกเป็นตัวเลือกที่ยาวที่สุดไม่เกิน 35% ของข้อ และสั้นที่สุดไม่เกิน 35% (บทเรียนจากเกมครัว: บทอ่าน 112/150 ข้อคำตอบถูกยาวสุด)
4. ไม่มีตัวเลือก "ถูกทุกข้อ/ไม่มีข้อใดถูก/ข้อ ก และ ข" เกิน 5% ของหน่วย
5. หน่วย `legal: true`: ต้องมี `sources` ครบ `title` `ref` `url` `verified_at` · เตือนเมื่อ `verified_at` เก่ากว่า 180 วัน · ผิดเมื่อ `valid_for` หมดอายุ
6. คำต้องห้ามในโจทย์และเหตุผล: "ข้อสอบจริง" "ออกสอบปี" "ข้อสอบปี 25xx" ชื่อชุดทดสอบ/แบรนด์ข้อสอบ
7. ตรวจข้อซ้ำ/ใกล้เคียงกันมาก (ความเหมือนของโจทย์หลังตัดช่องว่าง) ภายในสนาม
8. การกระจายระดับ (`level`) ต่อหน่วยอยู่ในช่วงที่คู่มือกำหนด · จำนวนข้อ `approved` ต่อหัวข้อพอสำหรับ blueprint (ไม่พอ = ชุดจำลองเปิดไม่ได้)
9. แบบวัดฟรีใช้ได้เฉพาะข้อ `approved` · `dist/` ต้องไม่มีฟิลด์ `why` `explain` หรือดัชนีข้อถูกของข้อใด (เทสต์ grep)
